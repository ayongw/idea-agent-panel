
## 一、阶段目标与核心原则

**目标**：基于 OpenCode Server 的 C/S 架构，在 IntelliJ 平台内构建一个 Tool Window 面板，实现对话交互、流式渲染、权限确认和上下文注入的完整闭环。

**核心原则**：

- **纯 Swing 原生 UI**：不使用 JCEF，所有界面组件基于 IntelliJ 平台内置的 Swing 组件体系，确保零额外依赖、全平台兼容、启动开销极低。JetBrains 官方推荐在插件 UI 中优先使用平台默认的 UI 框架。
- **状态与渲染分离**：消息列表管理和事件处理逻辑与 UI 渲染层解耦，为后续阶段复用奠定基础。
- **协议驱动**：以 OpenCode Server 的 HTTP API + SSE 事件流为唯一数据源，插件端只做“状态镜像”，不主动管理 AI 逻辑。


## 二、技术选型

| 决策点 | 选型 | 理由 |
|---|---|---|
| **插件语言** | Kotlin | IntelliJ 平台原生支持，与 IDE API 集成最佳 |
| **UI 框架** | Swing + JetBrains UI 组件 | 轻量、无额外依赖、风格与 IDE 完全统一 |
| **富文本渲染** | `JBHtmlPane` + `EditorTextField` | HTML 渲染文本，编辑器组件渲染代码块，保持语法高亮一致 |
| **HTTP 客户端** | OkHttp + `okhttp-sse` | OkHttp 官方 SSE 扩展库，完美模拟 SSE 客户端角色 |
| **进程管理** | `OSProcessHandler` | IntelliJ 平台内置 API，自动处理子进程生命周期和输出流 |
| **流式刷新** | 75ms 批量刷新定时器 | 避免每个 token 触发一次 EDT 更新，防止 UI 卡顿 |

**项目脚手架**：参考 JetBrains 官方模块化插件模板 `intellij-platform-modular-plugin-template`，该模板演示了如何将 UI 代码（frontend）与业务逻辑（backend）通过 RPC 分离，保持插件代码清晰。

**模块划分建议**（参考模块化模板）：

- **`shared`**：定义 DTO、事件模型、RPC 接口等跨模块契约。
- **`frontend`**：Tool Window 注册、Swing UI 组件、ViewModel、UI 状态管理。
- **`backend`**：OpenCode Server 进程管理、REST/SSE 客户端封装、消息状态逻辑、上下文注入。


## 四、核心模块实现

### 4.1 进程管理：启动与复用 OpenCode Server

插件启动时以子进程方式拉起 `opencode serve`，通过 `OSProcessHandler` 管理：

- **启动流程**：分配随机端口 → 创建 `GeneralCommandLine` → `new OSProcessHandler(commandLine)` → `startNotify()` → 轮询 `GET /global/health` 等待就绪。
- **复用策略**：启动前先检查本地是否已有 OpenCode Server 在运行（健康检查），有则直接复用，避免重复启动。
- **优雅终止**：在 `Disposable.dispose()` 中调用 `processHandler.destroyProcess()` 和 `killProcessTree()`，确保 Windows 上不残留文件锁定问题。
- **故障处理**：Server 启动失败时，在 Tool Window 中显示错误状态和重试按钮，并提供手动配置 Server 地址的入口。

### 4.2 通信层：REST 客户端 + SSE 监听器

**REST 客户端**（OkHttp）封装以下核心端点：

| 操作 | 端点 |
|---|---|
| 健康检查 | `GET /global/health` |
| 创建会话 | `POST /session` |
| 提交提示（异步） | `POST /session/{id}/prompt_async` |
| 获取消息（对账用） | `GET /session/{id}/message` |
| 回复权限 | `POST /session/{id}/permissions/{permissionID}` |
| 中止执行 | `POST /session/{id}/abort` |

**SSE 监听器**：使用 `okhttp-sse` 扩展库的 `EventSource` 和 `EventSources` 监听 `GET /global/event` 事件流。SSE 连接在后台线程运行（`ApplicationManager.getApplication().executeOnPooledThread()`），解析到的事件通过 `SwingUtilities.invokeLater()` 调度到 EDT 更新 UI。

**关键约束**：SSE 是尽力而为的，不可单独信任。必须定期通过 `GET /session/{id}/message` 对账权威消息状态，检查是否有遗漏的权限请求或消息部件。

### 4.3 对话面板 UI

使用 `ToolWindowFactory` 创建原生 Tool Window，内部用 `JBSplitter` 分为左右两栏：

**左侧 — 会话列表**：用 `JBList` 展示所有会话，支持创建、切换、删除。列表项显示会话标题、最后活动时间和状态图标。

**右侧 — 对话面板**（核心区域），从上到下：

**对话历史区**：`JBScrollPane` 包裹垂直布局的 `JPanel`，每个消息部件是独立子组件。文本渲染采用 **`JBHtmlPane` + `EditorTextField`** 的混合架构：

- **普通文本/Markdown**：通过 `org.jetbrains:markdown` 库转为 HTML，交给 `JBHtmlPane`（`com.intellij.ui.components.JBHtmlPane`）渲染。
- **代码块**：使用 `EditorTextField` 承载真实 IDE 语法高亮，这是 JetBrains 方案相比 WebView 的天然优势——代码块拥有与主编辑器完全一致的语法高亮和字体。
- **思考过程**：用可折叠的 `CollapsiblePanel` 展示，流式期间展开，结束后自动折叠。

**权限确认卡片**：在对话流中内联插入，**不使用模态对话框**。包含操作描述和三个按钮（允许一次 / 始终允许 / 拒绝）。OpenCode 的响应格式是 `once | always | reject`，点击后通过 REST 回传。

**输入区**：`JBTextArea` 配合 `JBPopup` 做历史记录，支持 `Ctrl+Enter` 发送、`Shift+Enter` 换行。输入区上方嵌入当前上下文标签（如“当前文件：UserService.java”）。

### 4.4 流式渲染策略

`text-delta` 和 `reasoning-delta` 事件高频到达，**不要每收到一个 token 就触发一次 EDT 更新**。推荐方案（参考 DevoxxGenie 插件的成熟实现）：

- 后台线程将增量文本追加到线程安全缓冲区。
- 启动一个 **75ms 间隔的 `javax.swing.Timer`**（在 EDT 上运行），定时从缓冲区读取内容并批量更新对应的 UI 组件。
- **首次收到 `text-start` 或 `reasoning-start` 时立即创建 UI 组件并渲染首屏**，确保用户感知到响应速度。
- 收到 `text-end` 或 `reasoning-end` 时做**最终无损 flush**，触发一次完整的 Markdown 渲染。

IntelliJ 平台也提供了 `DebouncedUpdates` 工具类用于批量处理 UI 更新，可作为 `javax.swing.Timer` 的替代方案。

### 4.5 上下文注入

通过 IntelliJ 的 `Editor`、`Project`、`PsiFile` API 获取当前编辑状态，注入到 OpenCode 的 prompt 中：

- 当前打开文件的路径和内容摘要
- 光标位置和选中代码
- 用户显式添加的上下文文件（右键菜单“Add to OpenCode Context”）

上下文以结构化格式附加在用户输入之前，或作为独立的 context 字段传递给 Server。可利用 PSI 进行更精确的代码语义分析，替代纯文本匹配。


## 五、关键风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| **SSE 事件丢失** | 权限请求或消息部件遗漏 | 定期通过 `GET /session/{id}/message` 对账；权限请求到达时在状态栏显示通知 |
| **Server 启动失败** | 插件不可用 | 提供手动配置 Server 地址的入口；健康检查 + 重试机制 |
| **流式渲染性能** | UI 卡顿 | 75ms 批量刷新 + EDT 调度；大量文本时限制渲染窗口 |
| **Windows 进程残留** | 文件锁定导致插件更新失败 | `dispose()` 中调用 `killProcessTree()` 确保进程树完全终止 |
| **OpenCode 版本升级** | API 不兼容 | 锁定 SDK 版本；关注 OpenCode release notes 和 API 变更 |

**最大的隐性风险是 UI 资产复用**。建议在第一阶段就将**状态管理逻辑**（消息列表、事件处理、对账逻辑）放入独立的 Kotlin 模块（`backend` 或 `shared`），与 UI 渲染层（`frontend`）解耦，为第二阶段独立桌面应用复用奠定基础。
