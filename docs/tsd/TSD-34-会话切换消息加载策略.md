## 1. 结论与总览

**只做 A（切换期反馈），B（消息快照缓存）与 C（最近 N 条窗口化）主动搁置。**

| 方案 | 内容 | 结论 |
|---|---|---|
| **A** | 切换期间显示细进度条 | ✅ **实施** —— 消除"点了没反应"的观感 |
| **B** | `Map<sessionId, List<ChatMessage>>` 快照缓存，省重复 REST | ⏸️ 搁置 —— 只省往返、不省重渲染；当前往返占比极小 |
| **C** | 只渲染最近 N 条 + 「加载更早」 | ⏸️ 搁置 —— 真风险是对账语义冲突，不是性能 |

### 重启触发阈值（满足任一即重开 B/C 评估）

1. 单会话气泡数 **> 300**；
2. 切会话肉眼可感延迟 **> 300ms**（本地 server，排除网络因素）；
3. 明确收到"长会话打开慢/卡"的用户反馈；
4. 单次 REST `getMessages` 响应体 **> 2MB**。

> 阈值写在这里而不是记忆里：下次有人问"为什么不做窗口化"，直接指回本文档与阈值，而不是重新做一轮评估。

## 3. 问题的真实形状

先纠正一个常见误解：**「切换会话慢」的瓶颈不是 REST往返，而是重渲染。**

当前切会话的实际路径（`ChatList.setMessages`）：

```
listModel.ids != groupIds          ← 会话不同必然成立
  ├─ removeDeletedGroups()         旧气泡 bubble.dispose() + 移除
  ├─ addNewGroupedMessages()       逐条 new MessageBubble(...)
  ├─ relayoutMessages()            removeAll + 按序重挂
  └─ requestLayout()               布局 + 几何自愈
scrollToBottom()                   无条件跳到底部
```

- 后端 `_messages` 是单`MutableStateFlow`，**无按会话缓存**；`loadMessages` 每次清空流式缓冲；
- 前端 `ChatList` 是**面板级单例**，所有 tab 共用；切换 = 整批气泡销毁重建；
- 因此**快照缓存（B）只能省掉 1 次 REST 往返，省不掉重建**。

已在批次 3 把切换从 3 次串行往返（`getSession → loadMessages → loadSessions`）降到 1 次，**这一刀比做缓存的收益大得多**。

## 4. A 方案：切换期反馈（本次实施）

### 4.1 问题
切换期间消息区**停在上一个会话**且无任何反馈（这是刻意设计：`loadMessages` 失败不清空，保证数据与当前会话一致）。叠加 1 次 RTT 的等待，用户感知就是"点了没反应"。

### 4.2 设计
- `SessionController` 增加 `isSwitchingFlow: StateFlow<Boolean>`，`switchSessionInternal` 期间置位（`finally` 复位，含失败路径）；
- `ChatList` 增加 `setSwitching(Boolean)`：在自身 NORTH 边挂一条**不确定进度条**，默认不可见；
- 不替换消息区卡片 → **旧内容留在原位、无闪烁**，只多一条顶部细线表示"正在加载"；
- 切回/切走都复位，避免残留。

### 4.3 不做
- 不做全屏遮罩 / 不做骨架屏（占位块）：RTT 本地仅几十~几百毫秒，全屏切换会闪，反而更差；
- 不在 EDT 上做耗时工作。

## 5. B 方案：消息快照缓存（搁置）

### 5.1 设想
frontend 维护 `Map<sessionId, List<ChatMessageDto>>`，切回已访问会话直接命中，不发 REST。

### 5.2 为什么现在不做
| 理由 | 说明 |
|---|---|
| 省错了对象 | 真正的大头是**气泡重建**，缓存不省这部分 |
| 收益小 | 中位 3 条 / 最大 14 条，1 次本地 RTT（~50ms）相对重建成本可忽略 |
| 失效复杂 | 会话被外部窗口新建/改名/删除、事件流补消息，都会让快照过期；需要额外的失效与一致性约定 |
| 内存无上限 | 长会话缓存整份消息列表，与 C 的目标（控制内存）方向相反 |

### 5.3 若将来要做，必须先定义
- 快照容量上限（LRU，按会话数还是总条数）；
- 失效触发点（收到事件流消息 / 会话列表变更 / 超过 TTL）；
- 与 `mergeReconcile` 对账的关系（快照命中时是否仍要对账）。

## 6. C 方案：最近 N 条窗口化（搁置）

### 6.1 设想
首屏只渲染最近 N 条气泡，上方提供「加载更早的消息」；服务端 `limit`/`cursor` 已支持。

### 6.2 为什么现在不做
**真风险不是性能，是正确性**：`mergeReconcile` 当前是**全量语义**

```
REST 全量覆盖同 id + 本地独有保留 + REST 缺失整段按时间插入
```

一旦本地只持有最近 N 条，对账会把窗口外的消息判成「REST 独有」而**全部补回来**，窗口失效且顺序错乱。⇒ **C 必须先重构对账为窗口化语义**（携带窗口边界、只对可见区间合并），不能当作"顺手加个 limit"来做。

### 6.3 若将来要做，前置重构清单
1. `MessageListModel` 支持前缀插入与窗口边界（`windowStartMessageId`）；
2. `mergeReconcile` 改为**区间合并**，窗口外消息不参与；
3. 事件流追加时判断是否落在窗口内（落在窗口外只更新计数，不建气泡）；
4. 「加载更早」与 `allSessionsFlow`/对账触发的并发去重；
5. 气泡虚拟化（窗口化后仍需组件数上限，否则只是把问题推后）。
